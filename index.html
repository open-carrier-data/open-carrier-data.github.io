Carrier settings as public data

Open Carrier Data is a public database of mobile carrier settings for open-source phone systems, kept as neutral JSON and generated into Android files.

Public repository Read the README on GitHub

This page is the front door. The README carries the details. Phones never load this site at runtime.

What you get today

The public repository holds three things you can use today.

Neutral carrier profiles as JSON

One file per carrier match under carriers/open/. Each profile carries match rules, capabilities, APN rows, and reviewed CarrierConfig values. Sources are merged into one carrier-centered record.

Generated Android files

generated/android/ holds apns-conf.xml, carrier-config-list.xml, carrier-config-overrides.json, carrier-id-index.json, lookup.json, mccmnc-index.json, and metadata.json. The APN XML targets database version 8.

A device catalog with honest status counts

generated/devices/ lists 42,401 Android devices and 183 Apple products. Every device carries one status that says how far carrier-data discovery got. A listed device is not a supported device.

Get the data

Pick the way that matches how much of the repository you want.

Clone and validate everything

To get the profiles, the generated files, and the tools, run this from any folder.

git clone https://github.com/open-carrier-data/open-carrier-data.git
cd open-carrier-data
python3 tools/validate_public_carrier_data.py carriers generated/index.json
python3 tools/validate_device_catalog.py generated/devices

Download one generated file

To take only the stable snapshot, which lists all 7,765 profiles, or one Android file, download it from the main branch.

curl -LO https://raw.githubusercontent.com/open-carrier-data/open-carrier-data/main/generated/index.json
curl -LO https://raw.githubusercontent.com/open-carrier-data/open-carrier-data/main/generated/android/apns-conf.xml

Resolve one SIM on your machine

To see the broad profile for a network code, run the resolver from the clone.

python3 tools/resolve_carrier_profiles.py --mccmnc 26202

The resolver also takes --spn, --gid1, --gid2, --iccid, --imsi, and --android-carrier-id. With --mccmnc alone it returns only the broad profile. Profiles keyed by SPN, GID, IMSI, or ICCID appear only when you pass those values, and the output lists matches in generic-to-specific order. A more specific profile is an overlay on the broad one, not a replacement.

How it is built

Data moves through five stages before it reaches the public repository.

  1. Sources. Maintained upstreams such as AOSP, LineageOS, GNOME, Apple, Google, and Samsung. Each source family has one upstream and a recorded check date.
  2. Private import. A private repository turns each source into candidate observations. Raw vendor files stay there.
  3. Sanitizer. One tool merges observations per carrier, drops private fields, quarantines stale or conflicting data, and writes neutral profiles.
  4. Public profiles. The result lands in carriers/open/ with an evidence index that names the source behind every fact and the exact revision of each public source snapshot. Samsung observations carry check dates in the device catalog index instead.
  5. Generated files. Generators build the Android files and the device catalog. Public CI runs the validators on every change to main and every pull request, and a daily job runs them in strict mode.

Read SOURCES.md for the merge rules and generated/evidence-index.json for the revisions behind the current snapshot.

Limits to read before you ship

Read these before you ship the data anywhere.

  • An MVNO without its own SPN, GID, or IMSI prefix in any source merges into the host network's profile. No profile names LIDL Connect, which runs on Vodafone Germany, so a LIDL Connect SIM resolves the 26202 profiles with Vodafone's settings.
  • When sources disagree on a CarrierConfig value, an add-on, or an APN row, the sanitizer omits the value instead of picking one. Conflicting capabilities become conditional. The evidence index records each omission.
  • The validators reject a source snapshot whose checked_at is older than 180 days when run with --freshness fail. A hosted job re-checks ten source families every week, but the window follows the oldest observation, a Samsung one from 2026-07-13, so from 2027-01-10 the daily public job fails that check and opens an issue labeled stale-data. Pushes and pull requests keep passing in warn mode. Samsung does not change by itself, and Samsung sets the window.
  • Listing is not support. A device in the catalog and a carrier in the profiles say where discovery got to, not that a feature works on that phone.
  • Some match rules cannot be expressed in Android XML. Those profiles stay in JSON and are listed in generated/android/metadata.json.

How to contribute

You do not need write access. If a carrier is missing or wrong, use the guided issue forms. One form is for wrong or missing carrier data, including a fix you tested yourself, one for a source suggestion, and one for docs or tooling. There is no automated path from a report into the data yet.

Never post phone numbers, account data, personal passwords, tokens, or private vendor credentials. Never post full IMSI or ICCID values, IMEI, serial numbers, raw logs, raw bugreports, raw firmware dumps, or private vendor responses. Safe details are the carrier name, country, MCC and MNC, SPN, GID prefix, and Android carrier ID. Public source links, the feature you tested, the result, and the test date help too.

The contribution guide and SECURITY.md describe the forms and the private reporting path.
